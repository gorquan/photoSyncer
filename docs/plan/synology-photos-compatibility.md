# photoSyncer 群晖 Photos 兼容设计

## 目标与边界

支持从小米云和 Apple iCloud 下载媒体，并将选定媒体导出到 Synology Photos 可索引的目录。兼容目标包括拍摄时间、方向、位置等原有元数据的保留，静态照片和视频的展示，以及动态照片的识别与播放。

同步成功需要区分三个层次：源文件下载完整、目标媒体导出完整、群晖实际识别并可播放。文件落盘或触发索引不能证明后两个目标已经实现。

当前设计以保留原件为前提。具体兼容范围需要通过目标 NAS 的 DSM、Synology Photos 版本和真实云端下载样本确定，不能对所有小米动态照片格式或所有客户端提前承诺完整支持。

## 两个厂商的处理策略

### Apple iCloud

普通照片、普通视频优先保留原始内容。实况照片应以逻辑照片为单位调度：原始静态照片和配套视频必须一起处理，并写入相同目录、使用相同主文件名，例如 `IMG_1234_a1b2.HEIC` 与 `IMG_1234_a1b2.MOV`。RAW 等替代资源使用独立角色名称，避免覆盖。

共享主文件名是目标环境中已验证的必要改动：DSM 7.3.2、Photos 1.9.1 下，6 组真实原件使用当前命名时产生 12 个分离项目；保持字节不变、仅改为共享主文件名后产生 6 个 `live_type=live` 项目。该结果限定于本轮样本和环境，不代表完整的群晖识别规范。

文件名不能替代配对元数据。Apple Live Photo 使用图片和 MOV 中关联的内容标识，MOV 还包含封面时刻相关的定时元数据。原件已有的信息应完整保留。6 组样本的图片与视频 ContentIdentifier 均匹配。

统一后缀应来自逻辑照片身份，例如厂商、账号、资料库或 zone、云端 asset ID 的稳定摘要，不能分别使用图片和视频的校验值。下载版本使用独立字段记录。

增加“包含实况/动态照片”的逻辑选择，使其配套视频不受“下载普通视频”开关影响。缺少任一必要组件时保留可重试状态，不把整个实况照片标记为成功导出。

当前 iCloud 实现获取的是选定原件资源，不等于完整镜像 Apple 相册里所有编辑版本、效果和虚拟相册状态。

### 原件完整性验证

CloudKit 官方将 `fileChecksum` 描述为上传步骤返回的文件签名，没有定义为下载明文的普通 SHA-1。本轮 12 个真实资源的值均为首字节 `0x01` 的 21 字节数据，但后 20 字节均不等于本地文件 SHA-1。独立重新查询下载链接并重新下载后，12 个文件的 SHA-256 全部与首次保留的文件一致，大小也全部匹配；因此不能继续使用现有算法判定这些文件损坏。

云端签名应作为不透明的来源版本字段保存。在没有实现并验证对应签名算法之前，以云端声明大小、HTTP 传输长度（可用时）、预期媒体类型和可读取结构检查传输结果，并保存独立计算的原件 SHA-256，用于存档后复核。大小和可解码检查不等价于服务端内容签名验证，界面及状态应明确验证依据。重复下载一致是本轮诊断证据，不应作为每次同步的必要步骤。

验证状态需要区分完整性检查通过、来源签名已验证、用户跳过检查及验证失败；现有 `sha1Verified` 同时表示成功与无需处理，不足以表达这些区别。未知签名不能按普通 SHA-1 比较后自动删除原件，也不能通过长期关闭校验掩盖问题。

### 小米云

小米官方动态照片格式文档描述了图片与视频位于同一个文件、通过 XMP 等信息描述视频位置和展示时刻的结构。群晖已公布 Android Motion Photo 支持，因此优先验证原件直接导出是否可用。

必须先检查从小米云实际下载的字节。手机本地支持动态照片，并不能证明云端下载接口仍返回完整动态内容。云端类型标志只能用于提示，不能替代结构检测。本轮响应实际使用 `description.specialTypeFlagsNew`。全量 4,617 条记录筛查后，已下载验证的 6 张新版动态原件对应 `:1073:1065:`，1 张旧版对应 `:1006:`；这是样本映射，不能把标记作为最终判断或排除其他格式的依据。

小米接入层应区分已观察到的两类失败：相册接口 HTTP 401、`isSecondValidation=true` 表示需继续官方身份验证；旧 `passToken` 无法换取服务令牌表示当前程序凭据不可用。官网已授权并能下载媒体，不等于程序旧会话自动获得访问权。需要识别业务响应并准确引导继续验证或更新凭据，不能仅报告普通 HTTP 错误，也不能以凭据交换成功判定相册已可访问。

项目真实下载链路已验证：重新扫码更新凭据后完成 DCIM 11 项下载，5 JPEG 和 6 MP4 的大小及独立普通 SHA-1 全部匹配；NAS 自动收录全部 11 项。另有 6 张 Xiaomi 14 相机 JPEG 作为格式诊断样本。JPEG 缩略图全部 ready，H.264 与 HEVC 普通视频各抽测一段在当前 macOS 群晖网页完播，视频缩略图仍为 ame_defect。全量记录筛查后又确认至少 7 张动态原件：6 张使用 MotionPhoto + GContainer，1 张使用 MicroVideoOffset；云端大小与 SHA-1、尾部视频长度和本地解码全部通过。这 7 个未改写原件在目标 Photos 上均显示 Motion Photo，网页逐项观察到实际解码和播放时间推进，缩略图全部 ready。首期对这两类格式采用原始单文件导出，不默认转换为 Apple Live Photo。移动端及其他格式继续按实际样本验证。

建议采用以下分支：

1. 普通照片：直接进入静态照片导出。
2. 完整动态照片且目标群晖识别通过：保留单文件原始结构直接导出。本轮的 MotionPhoto + GContainer 与 MicroVideoOffset 两类共 7 个原件已满足此分支。
3. 完整动态照片但目标群晖不识别：启用经过验证的转换配置，生成有效的 Live Photo 图片和 MOV 配对。
4. 只有动态标志、没有视频内容或结构损坏：明确报告静态降级或适配失败，不宣称动态照片同步成功。

解析应按 XMP、声明的尾部偏移和容器结构实现，并验证范围、长度及视频可解析性。需要考虑旧版 MicroVideoOffset、新版 Container 目录、小米扩展字段及增益图等差异，不能用第一个 JPEG 结束标志或搜索 `ftyp` 的方式盲目切分。

转换到 Live Photo 时，需要保留方向、拍摄时间、音轨和封面时刻，并正确构造关联标识及必要的定时元数据。将 `.mp4` 改名为 `.mov` 或只写入一个普通标签都不足以完成转换。本轮部分样本的 XMP 展示时刻超过嵌入视频报告时长，应先明确时间轴语义；无法确定时需显式记录降级，不能盲目写为 0 或越界时刻。编码兼容时优先重封装；HDR、HEVC 转换仅在明确的兼容配置下进行。

小米官方处理 SDK 面向 Android，不能直接假定适用于本项目的 Linux/JVM/GraalVM 运行环境。转换工具还需要单独验证依赖、许可及原生镜像兼容性。

## 共用群晖导出层

### 媒体与状态模型

保留现有 Asset 作为云端资源记录，增加逻辑照片分组及导出记录，不必立即重写所有厂商接口。

- 逻辑身份：厂商、账号、资料库或 zone、云端逻辑照片 ID。
- 资源角色：主图片、实况视频、RAW 或其他替代资源。
- 输入版本：云端校验值或版本，以及本地原件哈希。
- 导出记录：目标配置及处理器版本、输出文件清单、输出哈希、完成状态与错误。
- 相册关系：独立保留，不通过复制同一媒体到多个目录表达默认展示。

苹果通常是多个源资源组成一个照片；小米通常是一个源文件产生一个或多个导出文件。这两个关系应由共用模型表达。

### 处理流程

`下载到暂存区 → 校验源文件 → 探测格式并分组 → 目标适配 → 元数据和时间处理 → 发布全部输出 → 可选索引触发`

原件存档位于群晖索引目录之外。转换只作用于工作副本或导出副本，源校验值与导出校验值分别保存。不要对与原件共用 inode 的硬链接执行原地元数据修改。

临时文件也应位于索引目录之外，避免群晖提前扫描半成品。多个文件无法通过普通文件系统操作整体原子发布，应使用持久化的组状态和重试修复。配套视频先发布、静态图片后发布可以减少中间状态，但不能保证群晖一定看不到中间状态。

转换失败可直接使用本地原件重试；修改导出规则后可以重新导出，无需重新下载云端文件。已经完成的旧任务也必须能按新导出版本重新评估，不能仅依赖原有完成记录或“路径已存在”。

小米当前校验阶段跳过 SHA-1。本轮 11 个项目下载文件、6 个相机诊断文件及额外 15 张 JPEG 的本地普通 SHA-1 均与云端 `sha1` 相同，为实现来源校验提供了实测依据；应只对明确声明该校验算法的原件比较，并补充失败处理验证。不能把原始校验值用于转换后的文件，也不能把现有“跳过”状态当作已验证。

### 元数据与时间

优先保留已有 EXIF、XMP、QuickTime 元数据，仅在缺失且来源明确时补齐。文件名日期不能覆盖已有拍摄时间；云端时间和文件内时间冲突时需要明确策略。

文件修改时间设置为拍摄时间，作为索引排序的辅助信息。视频 UTC 时间和时区偏移要区分处理。文件系统不支持 birthtime 时应降级为设置 mtime，不能因可选时间属性导致全部导出失败。

动态照片写入元数据前先检测格式，写入后再次验证视频范围和配对关系。不能未经验证对带视频尾部的文件直接执行通用 EXIF 重写。

### 目录和去重

目标为群晖个人空间 `/home/Photos` 或共享空间 `/photo` 对应的实际 NAS 路径，通过 Docker 挂载为应用输出目录，例如 `/photos`。实际卷名和用户目录按部署环境配置，并确认群晖用户具有读取权限。

推荐默认按厂商、账号、拍摄年月导出一份实体文件，例如：

```text
/photos/Apple/account-1/2026/10/IMG_1234_a1b2.HEIC
/photos/Apple/account-1/2026/10/IMG_1234_a1b2.MOV
/photos/Xiaomi/account-1/2026/10/IMG_5678_c3d4.jpg
```

同一云端照片出现在全部照片、收藏、自建相册中时只导出一次。相册目录模式可以作为选项，但需要说明重复展示的影响。不能仅凭文件名或拍摄时间跨厂商去重。

云相册、收藏、人脸标签与群晖的虚拟相册并非同一系统，复制文件不会自动迁移这些关系。首期兼容范围应聚焦媒体文件本身。

### HEIC、HEVC 与预览

文件可索引、动态照片可配对、浏览器可显示缩略图和视频可播放是不同问题。群晖官方说明，部分版本下 HEIC/HEVC 预览需要 Synology Image Assistant 等处理。

目标 NAS 的真实结果为：同名组 6 项均完成配对，5 项 JPEG 缩略图为 `ready`，1 项 HEIC 为 `ame_defect`；分离组的视频预览也为 `ame_defect`。Photos 设置报告 NAS 的 H.264/HEVC 能力与相关组件均不可用，但当前 macOS 浏览器抽测的 H.264 实况视频与分离 HEVC 原件均可播放。HEIC 页面明确要求 Image Assistant 生成 JPEG 预览。这表明当前环境存在独立的预览能力缺口，不能把服务器预览状态与客户端播放能力混为一谈。详细范围见实机验证记录。

首选保留原件并使用群晖支持的预览生成路径。如果目标环境需要 JPEG/H.264 等兼容副本，应建立独立的兼容导出配置，同时验证色彩、HDR、方向和动态配对。不要把原 HEIC 和转换出的 JPEG 默认一起放进同一索引目录，否则可能出现重复照片。

现有 Docker 镜像只有 ExifTool，转换需要按功能增加并验证 ffmpeg、图像解码器或其他组件。容器格式兼容不等于视频编码兼容。

### 索引触发

参考项目 `boredazfcuk/docker-icloudpd` 的 `synology_photos_app_fix` 针对本轮新下载的 HEIC，通过暂时修改文件时间再恢复来触发文件变化。这属于可选索引兼容措施，不能修复缺失的视频、配对元数据或解码能力。

可在资源组全部发布后提供类似处理，避免逐组件过早触发。需要验证本项目通过挂载目录写入时的实际效果；仅设置 mtime 的具体实现不一定等价于参考脚本的行为。索引触发失败与媒体适配失败分别记录，触发成功不能标记为群晖已确认收录。

首期无需直接写入群晖数据库、`@eaDir` 或依赖未公开 API，也无需为了导出媒体给容器特权权限。

## 实施顺序与验收

1. **修复同步前置问题并补齐样本**：修复 Apple 校验误判及小米认证状态处理、启用有实测依据的小米原件 SHA-1 校验；以已获得的两个厂商真实媒体基线回归，并用现已取得的 MotionPhoto、MicroVideo 两种小米动态原件回归。
2. **完成共用分组及苹果导出**：稳定共享名称、原始配对元数据保留、独立的动态照片开关、成组完成判定、重复相册去重、旧任务重新导出。
3. **完成小米原生动态导出**：优先支持实测通过的 MotionPhoto + GContainer 和 MicroVideoOffset，检测视频边界并保持原件；对不支持或缺失视频提供准确状态。不得通过通用 EXIF 改写破坏原始尾部结构。
4. **按验证结果增加转换和预览配置**：只为已确认存在的兼容缺口增加转换，分别验证群晖网页和移动端。
5. **补充发布恢复与索引措施**：验证断电或中断后的配对修复、资源版本更新、规则升级及索引触发。

样本应覆盖 JPEG、HEIC、截图、H.264/HEVC 普通视频、Apple Live Photo、小米不同版本动态照片，以及旋转、GPS、时区、HDR、RAW 替代资源、同名文件、重叠相册、缺失配套视频和损坏尾部。

自动验证检查文件完整性、配对标识、时间、可解码性和重试行为；最终通过真实 Synology Photos 检查时间轴、缩略图、动态播放和重复数量。小米单文件动态照片在本轮列表 API 中仍为 type=photo，应以网页 Motion Photo 控件及实际播放为依据，不能复用 Apple 的 type=live 判定。未取得真实云端样本及目标群晖版本之前，不能把代码层面的检查结果描述为已完成群晖兼容。
